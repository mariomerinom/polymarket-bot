- `src/fill_diagnostic.py` — SQLite-based fill instrumentation: `init_table`, `record`, `fill_rate`, `fill_outcome_correlation`. Extended RESULT_CODES to cover FAK outcomes, skip reasons, and error paths.

- `src/botsy_engine.py` — `_maybe_run_daily_rollover()` fires once per asset per UTC day from the bybit_spot 5m dispatch path; runs REST fetch + compute + record in a thread to avoid blocking the WS loop.

## What We Learned

- **Selection is not the problem.** 30-day BTC 5m: placed 67.0% WR counterfactual vs skipped 64.7% → our bet-selection filters are mildly POSITIVE. Anti-selection thesis is ruled out.
- **Fill cost is ~$1,000 on 91 bets.** Signal says +$843 P&L (counterfactual) but actual live P&L was ~-$150 on those same bets. The gap is execution drag, not signal noise. This confirms the Lever B fill thesis.
- **BTC chop+UP is the sweet cell.** `signal_pnl --group day_type`: chop UP = 77.7% WR / +$12.83/bet. BTC vol_hi DOWN = 47.7% WR / -$4.60/bet (only losing cell). These are the first `asset_daily` insights and justify the table's existence.
- **ETH inverts BTC's daily pattern.** ETH shows reversed day_type performance relative to BTC — same trend label, opposite edge direction. This is worth investigating before any conviction-gating work.
- **Paper P&L was previously broken.** Old paper orders had `NULL` P&L because `compute_order_pnl` only settled live rows. Today's fix uses optimistic fill at `price_limit` for paper, keeping paper P&L as the upper-bound signal estimate — correctly separated from fill quality.
